# AI Station contributor guidance

The 2026-10-25 product decision in `docs/plans/unified-assistant-chat.md` removes
the user-facing Chat/Work split. Deliver one conversation; the orchestrator chooses
direct replies versus applicable tools/workflows. Preserve scoped permissions,
approvals, history and legacy API compatibility; do not add new mode switches.

Product priorities follow `docs/plans/agent-first-product.md` (user decision, 2026-10-15): focus on useful persistent agents with local code execution; defer standalone IDE/Coding expansion and further Cursor/Codex integration work. Reuse and preserve existing coding services, projects and records.

Read `docs/architecture.md`, `docs/security-model.md`, and `README.md` before changing execution boundaries.

- Preserve the modular monolith: Docker control plane, native user-level Host Runner, typed HTTP over a private Unix socket.
- All workloads use Task → Run → Events → Artifacts. HTTP handlers enqueue; workers execute.
- Keep app-owned paths relative to the data root. Validate canonical host paths and symlink boundaries.
- Never expose arbitrary commands, Docker control, or unrestricted host mounts. Never modify external runtimes, models, drivers, or `reference/photo_pipe.py` to make tests pass.
- New schema changes require Alembic migrations. Use temporary databases and fake executors in normal tests; expensive integrations must be explicitly opted in.
- Treat unfinished adapters as unavailable until their permissions, cancellation, and recovery contracts are tested. Do not report unexecuted smoke tests as successful.
- Work on feature/fix branches. PRs target `develop`; review the full diff and pass validation before squash merging. Hosted Actions are currently manual because the user has exhausted free credits and explicitly authorized local verification instead (2026-09-28). Run `./scripts/check-all.sh` or document equivalent successful local checks for the reviewed head; do not treat actual test failures as waived. Never push or merge to `main` or `master`.
- Run `./scripts/check.sh` for backend/runner changes; frontend changes also require lint, typecheck, and a production build. Validate Compose and the Docker image when deployment files change.
- The optional owner-dispatched `macos-native-checks` and separate `macos-native-inference` workflow operations are restricted to PUBLIC repositories and fixed standard free Mac labels. Only the latter opts into its pinned public CPU model fixture; ordinary checks run no real model. They do not re-enable automatic CI or paid/private/larger runners. Native test failures remain failures; hosted native evidence does not qualify Docker Desktop, Metal inference or the consumer installer.
- The separate `macos-desktop-transport` developer operation is restricted to a fresh standard free PUBLIC Intel VM in this repository. It refuses an existing Docker installation/configuration, installs only the hash-pinned Docker Desktop prerequisite using its documented administrator/license setup, and exercises the existing disposable socket/filesystem probe. This is not a consumer setup path or permission to change the development workstation; it runs no AI model and does not qualify the full Mac installer.
- The optional `macos-native-ui-checks` operation builds stock native source in a test app and drives its windows using Apple XCTest on a standard free PUBLIC Intel host. It runs no model or Docker and changes no OS/TCC permissions. Missing UI automation access remains a failed qualification, not a skipped/pass result. This component check alone does not qualify the full installed Mac package.
- The manual `macos-consumer-backend` experiment uses only a fresh standard free PUBLIC Intel host in this repository. It retains the fixed Docker Desktop installation guards, builds the actual package and explicitly opts into the pinned public 4B CPU model (2,497,281,312 bytes, catalog SHA256 enforced). It uses the existing console entry for real backend/account/model/restart evidence, not consumer GUI qualification. It may not run on the development workstation, change existing Docker installations or enable paid runners. The complete consumer gate also needs GUI, preserving update, backup/restore and removal acceptance.
- Only that optional backend job may use `statuses: write` for bounded stage/RAM/swap/disk evidence on its own commit and run context. Its short-lived token stays in the publisher and is removed before build/application/model subprocesses. A cold Desktop restart is allowed only for the new QA installation bound to that same run's private receipt, never an existing station. Status evidence alone cannot qualify the installer.
- Its optional `macos-consumer-gui` mode uses the same fresh public/free Intel guards and pinned model. It starts the stock app without console flags, attaches XCTest to the actual native helper/default browser and creates the first administrator through the visible form. Engine/model/chat assertions still use the ordinary API for now; neither mode may claim complete guided GUI/update/backup/removal qualification from that partial coverage.
- Keep startup instructions and implementation status accurate. Preserve existing work and make focused changes.
- Only the human owner @jahu may approve and merge PRs into `master`. Agents prepare reviewed release PRs and wait; authenticating as @jahu is not human approval. See `docs/release-policy.md`.
- Prepare `develop` → `master` PRs as `github-actions[bot]` with `gh workflow run ci.yml --ref develop -f operation=release-pr`; do not create them with the owner's CLI identity, which cannot self-approve. Review and validation precede dispatch.
- External contributions require the separately signed commercial-relicensing permission described in `CONTRIBUTING.md` before merge. A PR or DCO sign-off alone is insufficient.
