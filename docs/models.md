# Model files, definitions and installation

## Discover public model sources

The next-release discovery increment adds **Models → Find new models**
(`/models/discover`). Search public Hugging Face repositories or paste a
repository/file link. An administrator explicitly starts a private metadata-only
Task/Run; saved review URLs restore results without another source request.
The worker resolves a commit and available SHA256/size identities, records source
and license links, and compares exact objects with reviewed installation profiles.
Stop, account revocation, worker-claim replacement and deadlines fence publication.
No weight download, runtime preparation or inference is performed by inspection.

Choose a variant to inspect its file budget, supported profile and estimated
context/GPU group. A supported repository's publisher configuration is resolved
once and frozen for all its file variants. Hardware advice compares their fitted
32K context, required GPU count and an explicit balanced-quantization preference.
A useful known-precision GPU profile ranks before a low-bit alternative; unknown
requirements, missing telemetry or insufficient disk never earn a recommendation.
This comparison is within one model, not a speed or quality ranking across models.
**Context options** can request 128K for the installation plan; the model's trained
limit and actual fitted context remain visible. An old accepted plan retains its
original context target. GPU pairs are considered only through the existing
llama.cpp sharding admission, and short-cache fit is not called a full-context fit.
Matching platform profiles come first; Mac-only profiles are
not offered on Linux. Current GPU occupation is separate from capacity. Unknown
architectures and companion sets retain **unknown** memory requirements; a GGUF
extension or a file fitting on disk does not qualify it for Chat or Images.
Reviewed profile matches link to the existing guided setup. **Review installation**
also resolves a new single-file GGUF outside that catalog. Supported llama.cpp
planning families are Llama/Mistral, Qwen2, Qwen3 and Qwen3.5. The publisher must
declare a compatible causal-model configuration; embedding models, vision
projectors, ambiguous base models and incomplete shards are not installed as Chat.
The configuration's repository/commit/hash, weight SHA256/size, source and license
are frozen before the administrator accepts a download. GPU fit and storage are
checked again by the existing downloader. The native Runner must agree with the
actual GGUF's architecture, context and cache geometry before registry publication.
No downloaded Python, custom-code flag or arbitrary runtime is admitted.

New downloads use the existing model preparation history and Stop/Resume. Their
verified files/definitions appear in the shared Chat catalog; **Open Chat with
this model** creates a conversation without changing personal defaults. Other
accounts cannot inspect the source/plan/download history. Media recipe slots,
general discovery ranking and multimodal binding remain required steps of
[the complete next-release plan](plans/open-model-discovery.md).

Verification uses bounded fake public metadata, real private-account API/worker
tests and temporary storage. Live HF metadata/search and read-only workstation
telemetry were checked without weights or inference. Compiled desktop/mobile UI
checks use those public metadata results with fixture HTTP/hardware; they are not
a production model installation or inference qualification. The variant-advice
increment additionally checked all nine public Qwen2.5 0.5B GGUF files against
read-only actual GPU/RAM/disk observations. It selected Q6_K for a 32K target;
compiled desktop/mobile checks covered the recommendation, explicit 128K plan,
license consent and saved preparation restoration with fixture HTTP. No additional
weights or inference were needed to verify this assessment change.

A separate explicit real qualification built the Docker control plane and used
an independent native Runner/data root. It downloaded a fresh 491,400,032-byte
Qwen2.5 0.5B Q4_K_M from the publisher, resolved a new plan outside curated IDs,
verified/adopted it through the native GGUF contract, exposed it in Chat and
obtained `model import works.` from an actual GPU conversation. The route took
32 seconds on this workstation with the runtime image already installed; this
is not a general performance promise or a recommendation for complex agents.
Only its newly owned runtime was stopped; production data was untouched. Browser
installation/consent/progress/refresh checks replay the exact saved projections
without repeating the download or inference. Private evidence:
`data/acceptance/model-discovery-20261104/`.

## Native media checkpoint admission

The existing typed model verifier has an optional `checkpoint_profile` for a
fixed Qwen Image 2.1 diffusion slot. It admits only verified app-owned objects,
checks all tensor names/dimensions against a fingerprint of the exact qualified
reference, and validates allowed GGML storage layouts, alignment, extents and
non-overlap. Language-model context inspection shares the same bounded reader
and keeps its existing metadata-only contract.

A filename or `general.architecture` tag is insufficient: the existing Qwen2.1
reference has no architecture metadata, while the existing Lustify GGUF declares
`qwen_image` but has a different graph. The read-only real-file check confirmed
the Qwen reference's recipe SHA256/size and 297-tensor signature, and refused the
430-tensor Lustify graph for that slot. No weights were downloaded, altered or
loaded; normal tests use tiny synthetic GGUFs. The inspection result explicitly
does **not** qualify inference. New image installation uses this coordinate before
registry publication. Compatible
Qwen Image 2.1 GGUF sources resolve their publisher transformer configuration,
reviewed engine image and complete companion recipe. The existing resumable
model downloader installs the checkpoint; a required image-engine preparation
Run is a prerequisite in the same private Task. Stop covers both stages; Resume
refuses uncertain earlier engine cleanup. Existing verified objects are reused.
The initial engine recipe includes its starter checkpoint, fixed encoders, VAE
and upscaler; the review shows those files/licenses and the additional disk
reserve after verified cache reuse, including unpacked engine space. No personal
default is changed.

After native verification, the image definition is shared while source, planning,
installation and preparation history remain private. **Open Images with this
model** preselects it; ordinary assistant/agent image choices use the same registry.
Generate, Edit and Recompose freeze the owned checkpoint and fixed engine binding.
Their existing managed executor substitutes only the diffusion mount, with no
publisher code, alternate container or custom command. The native dispatcher
rechecks the graph, immutable source and each GPU component budget before start.
The reviewed profile uses two GPUs, a maximum 1024 pixels per side and the fixed
CUDA component placement. Larger checkpoint residency increases the primary-GPU
budget; it is never spread across cards by adding their VRAM. RAM is reserved and
the owned container's equal RAM/swap limits remain explicit. Existing configured
image pipelines and their definitions keep their previous behavior.

The normal API/worker tests use synthetic weights, the real native descriptor
parser and fake inference. They cover installation, engine dependencies, Stop,
Resume, uncertain cleanup, re-check, shared model/private history, Generate, Edit
and multi-reference Recompose. A separate explicit real qualification used an
isolated Docker control plane, native Runner and data root on this workstation.
It installed a new `qwen-image-2.1-Q4_0.gguf` object, exercised the normal engine
prerequisite and obtained actual 512×512 Generate, Edit and two-reference
Recompose results on the two NVIDIA GPUs. The native journals confirmed the
selected checkpoint, fixed CUDA component placement and equal RAM/swap limits,
without a CPU-offload flag. All test jobs finished and the test Runner stopped.
The engine image and three temporary verified companion copies were available
before preparation; the exact VAE, upscaler and new checkpoint used ordinary
verified downloads. This is not a fresh all-files download benchmark or Windows
GPU qualification. A final source/plan-only check reused that same installation
and confirmed zero additional engine/companion bytes, without another download
or inference. Browser desktop/mobile checks replay saved source/plan/state
projections, with no additional inference. Private evidence remains under
`data/acceptance/model-discovery-20261104/`.

The first qualification attempt completed installation but its harness supplied
a seed field rejected by the existing Qwen API. No generation had been queued.
After confirmed native cleanup, the request was corrected to match the workspace
and reused the same verified objects; all three GPU operations then succeeded.


### Native video checkpoint inspection (next release)

The fixed Wan 2.2 5B diffusion slot now has a bounded SafeTensors descriptor
inspection using the existing typed model-verification operation. It checks the
complete 825-tensor name/shape signature, F16 storage, exact byte extents, full
payload coverage and the fixed engine/companion recipe identity. Duplicate JSON
keys, unsupported storage, overlapping/holey/truncated buffers and unindexed
trailing bytes are refused. No tensor payload, Torch, publisher code or GPU is
loaded. The parser follows the [SafeTensors format](https://github.com/safetensors/safetensors#format).
Only immutable app-owned store objects may use this API coordinate; legacy LLM
inspection and activation remain GGUF-only.

Read-only inspection of the existing Wan reference confirmed its recipe SHA256,
825-tensor signature and 83,424-byte header. This is structural evidence, **not**
a new video installation path or inference qualification. New source plans,
companion preparation, explicit workload/offload consent and video/film/agent
selection still need to be connected before a discovered checkpoint is usable.


### Discovered video models (candidate under qualification)

A specific SafeTensors file can now be planned from its actual immutable header,
including publishers with no model card/base-model declaration. Two exact HTTP
ranges retrieve only the length and bounded JSON header; ignored/changed ranges
are rejected. Native slot matching checks the complete Wan 2.2 5B graph and F16
storage before a weight transfer. The accepted plan freezes the header digest,
full file identity and complete native engine/companion recipe. Native inspection
rechecks the same header digest and graph after the verified download.

The normal model Task may own a fixed video-engine prerequisite. Source and
component licenses plus the workload require explicit acceptance. The current
profile deliberately uses CPU offload, one 12-GiB GPU, at least 24-GiB physical
RAM, a zero-swap 11-GiB process scope, 1280×704 output and at least 20 steps.
Its existing bounded engine controls loading precision. This is not full GPU
residency or multi-GPU sharding. Missing sensors and two smaller cards cannot
satisfy that single-device requirement. The disk review includes missing runtime
inputs and working reserve; the engine's starter weights remain a prerequisite.

A registered video choice binds its owned checkpoint to the original opaque
engine identity. Video, longer films and reviewed agent/conversation media
settings share one selector. Every segment and Resume retain that source;
renaming the definition does not change execution identity. Explicit selection
can use its prepared engine while preserving existing configured/default video
behavior. Native parent/child dispatch checks the source, graph, engine, resources,
permissions and deadline; only the diffusion path changes. Owned process
inspection/cancellation/recovery stay on the existing ProcessManager protocol.
Re-check verifies the existing object and engine without another download.

Unit/native process tests use tiny weights and a fake inference executable.
A live public-HF range check verified an 83,424-byte header without model tensor
payload. Actual GPU qualification of this import path is still in progress;
0.1.2 packages and production preview are unchanged. FP8/GGUF/sharded video files,
other Wan architectures and other media families require their own supported
slots and complete plans, not this F16 admission path.

## Installed files

The Models workspace lists external files from the Host Runner's configured `AI_STATION_MODEL_ROOTS`. Observed files and curated definitions are each one keyboard sequence (arrows, Home, End, Enter inspects) with unique Inspect names; decorative type icons stay out of the tab order. `POST /api/models/discover` only enqueues a Task/Run. The worker dispatches the typed `/v1/runs/model-scan` endpoint with `filesystem_read` and `manage_models` permissions; callers cannot supply paths, commands or output locations. The runner owns a separate process group and applies the same durable identity, byte-offset logs, cancellation and conservative recovery rules as other native work.

Discovery uses descriptor-relative metadata inspection, does not open model contents, skips symlink files/directories and non-regular files, and rejects traversal into a different filesystem. Mount roots can be configured explicitly. It is bounded to 100,000 traversed entries, 5,000 models and a 60-second traversal budget. Filesystem calls blocked in the kernel can exceed the traversal budget; owned-process cancellation remains available. Models are never loaded, moved, renamed, deleted, copied or downloaded. UUID report paths remain under app-owned artifact storage and reject symlink redirection. The previous synchronous scan endpoint is no longer operational.

A known successful process exit and validated report are required before the worker updates the registry. The JSON inventory becomes a normal artifact. Partial scans, errors and cancellation do not overwrite the previous registry. Each file retains a stable ID, first-discovered timestamp, last-seen timestamp, latest observation Run and status:

- `present`: found in the completed scan; this is an observation, not a live loaded state.
- `missing`: not found under a root that completed its scan.
- `unknown`: the root was unavailable or is no longer configured.

Removed external files remain visible for inspection; no destructive endpoint is exposed. Search is literal filename matching, and category filters/pagination run in SQL. Categories, family, quantization and capability hints are inferred from configured root/filename conventions and are labelled as hints, not verified runtime compatibility.

## Definitions, presets and compatibility

Model File, Model Definition, Runtime and Runtime Instance remain separate records. Discovery creates Model File observations only. It does not invent curated model definitions or claim existing runtimes are managed.

A definition is created by an explicit UI/API action from a file observed as `present`. It stores a display name, inherited family/category/capability hints, and a load preset (`gpus`, `context_size`, `cache_type`). One definition is linked to one file. Removing the definition does not delete the file.

`GET /api/models/compatibility` returns declared format/category pairings with a runtime family. Those rows are labels, not a successful load, health probe or proof that weights run on this workstation. GGUF language models (except `mmproj` companions) declare the managed llama.cpp adapter. Other formats stay catalogued until a real adapter exists.

## Explicit installation

`POST /api/models/definitions/{id}/install` enqueues a Task/Run (`models.install`) with `filesystem_read` and `manage_models`. The worker calls the typed Host Runner `/v1/models/verify` endpoint. Callers cannot supply roots, commands, pull flags or output paths. The runner stats the snapshotted path inside configured model roots, rejects symlinks and non-regular files, and does not open model contents.

For GGUF language models it also inspects the administrator-configured llama.cpp image ID. Missing images fail closed. The runner never runs `docker pull`, never copies GGUFs and never starts a runtime. A JSON report becomes a normal artifact. Cancellation, errors and a changed size/mtime leave the definition unregistered (`unverified` or `failed`) and do not rewrite discovery observations. Retry is a new Run.

`POST /api/models/definitions/{id}/load` reuses the existing owned llama.cpp load Run with the saved preset. It requires a successful install and a present loadable GGUF.

Owned llama.cpp health and restart are separate inspectable Runs. Health records process liveness and observed context without signalling external runtimes. Restart unloads an idle owned instance, then loads the saved GPU/context preset. Unknown ownership still requires inspection. System diagnostics remain available for the host.

Migration `0002` adds nullable observation timestamps/Run links and an `unknown` default for pre-existing rows. Migration `0018` adds definition status, verification Run links and timestamps. Upgrade/downgrade coverage verifies existing file metadata survives. Tests use disposable small fixtures, real managed subprocesses and an in-process typed runner transport. The browser smoke uses a native runner over UDS and a worker. Neither test loads model weights or pulls images.
