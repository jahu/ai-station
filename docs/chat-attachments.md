# Attachments in local Chat

The composer reads explicitly selected files in the browser. The API accepts structured filename/content pairs, never a host path or URL. Up to four files are allowed. Duplicate names, path-like names and oversized serialized context are rejected before creating messages or Runs.

UTF-8 text/code remains 16,000 bytes each and 24,000 combined. PDFs are at most 1 MiB with eight pages; only extractable text is sent, capped at 16,000 bytes per file. PNG/JPEG/WebP images are at most 2 MiB and 4 megapixels; they are stored as artifacts and are **not** sent as pixels to the local text model. Encrypted, scanned or image-only PDFs fail closed rather than pretending the model viewed pages. SVG/HTML are not accepted as images.

Arrow keys, Home and End move through staged composer attachments; Remove stays on the selected file. Enter does not send and there is no inspectable attachment Run. Attachments already saved on a message are a nested keyboard sequence in the transcript with unique Saved attachment names; Enter opens the selected file and does not inspect a Run. The original user prompt remains visible separately. A bounded JSON representation of attachment names and untrusted reference text is persisted in the user message and snapshotted into the ordinary Chat Run context. PDF entries are labeled extracted text. Image entries state that pixels were not sent and instruct the model not to claim it viewed them. Existing recent-message windows, cancellation and local-provider restrictions apply unchanged. Regeneration reuses the same persisted source text; summary coverage includes extracted PDF and text rather than silently discarding it. Attachments in another conversation never enter this context.

Each upload is also an Artifact with a UUID storage filename, hash, original filename, source conversation/message and initial Run. Text storage always uses `.txt` and `text/plain`; PDFs keep `application/pdf` with attachment disposition; images keep their decoded type and a thumbnail. Downloads use `nosniff`. The browser does not render uploaded markup. No separate execution engine or migration is introduced.

A model may misunderstand file contents; attachment boundaries are context labels, not a guarantee against prompt injection. This slice is not vision analysis. The Chat executor has no tools or host filesystem access.
