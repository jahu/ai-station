# Projects

Projects register existing host Git repositories without copying or changing them. The control plane stores metadata and trusted validation commands; only the Host Runner resolves and inspects host paths inside configured roots. Registration stores the canonical worktree root returned by the runner, preventing duplicate registrations through subdirectories or aliases.

The Projects list is one keyboard sequence (arrows, Home, End, Enter inspects) with unique Inspect names; decorative repository icons stay out of the tab order. Git workflow policy checkboxes reuse that sequence with unique Policy names; Space or Enter selects the focused row and does not invent a commit, push, or PR Run. Linked agents on a project reuse that sequence with unique Inspect agent names; Enter inspects the selected definition. View tagged Runs stays on that row. View all linked agents opens the Agents filter through `GET /api/agents?project_id=`. Linking tags Runs and does not grant coding, Git or repository access. That list does not Enable or Run now. The first Projects slice provides registration, persisted configuration, and explicit read-only status refresh. Repository paths are immutable after registration. Name, branches, executor preference, structured test/lint/build argv, agent rules, and PR policy can be edited with an optimistic version check. A stale editor must reload; configuration changes are refused while a project has an active Run. Commands and policies are configuration only: saving does not run commands, launch coding agents, create worktrees, commit, push, or open PRs. A separate explicit preparation action creates an ordinary Task/Run and an owned worktree from the stored integration branch; unused owned worktrees expire after seven days unless kept, and an explicit removal Run deletes only that owned checkout and local task branch. Declared Python dependencies are installed into that worktree by another explicit Run. See [owned worktrees](worktrees.md) and [dependency installation](coding-boundary.md).

`main`, `master`, and the configured default branch are always protected. Force push, automatic merge, and production PR policy cannot be enabled. Preferences for task-branch push and integration PR creation remain stored intent for the future coding workflow, not authorization to execute now.

Host inspection occurs outside database transactions. Runner failure leaves saved metadata available and reports the live-state error instead of showing a clean repository. Status responses include the inspection time; status is not persisted as current truth. The API provides paginated listing, registration, detail, configuration replacement, and status endpoints under `/api/projects`. Configuration changes do not create Runs because they execute no workload; future coding tasks must use the shared Task/Run infrastructure.

Set `AI_STATION_ALLOWED_ROOTS` to include the repository and its Git metadata, then restart the runner. AI Station itself can be registered using its host checkout path. Registering it does not apply code changes or restart the running application. The read-only Git limits and unsupported partial-clone/alternate-store cases are documented in [security boundaries](security-model.md).

This uses the existing Project schema and its `updated_at` version; no schema migration is needed. Duplicate checks and updates use the current short, serialized SQLite transactions. A future PostgreSQL implementation must preserve atomic uniqueness and compare-and-update semantics. Branch names are validated syntactically, but configured branches need not exist yet; worktree preparation resolves its chosen local base at dispatch and fails if it is missing.
