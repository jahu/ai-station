# Local chat execution

Chat uses the existing Conversation and Message tables and the common Task → Run → Events infrastructure. No schema migration is needed for this slice. Enqueueing persists the user's message, an empty assistant message, and an immutable snapshot of model, endpoint, generation settings, and selected context. The worker performs HTTP inference; API handlers never generate completions.

`LocalChatProvider` adapts the [llama.cpp-compatible Chat Completions protocol](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md#post-v1chatcompletions-openai-compatible-chat-completions-api), without coupling the chat domain to a particular local runtime. Model discovery uses `/models`; streaming uses `/chat/completions`. Endpoint configuration is administrator controlled. URLs cannot contain credentials, query strings, or fragments. Only loopback, RFC1918/ULA addresses, localhost, and the Docker host gateway alias are accepted. HTTP proxy environment settings and redirects are disabled. Provider errors omit response bodies and credentials. A configuration change after enqueueing fails the Run instead of rerouting its prompt.

Each delta updates the assistant message and emits `chat.delta`. Partial text survives provider failure, cancellation, and worker loss. Connection cancellation is checked at most every 250 ms while awaiting provider data, subject to DB scheduling; the HTTP stream is closed on exit. It does not stop or reconfigure the external model server. A completion has a ten-minute wall-time limit, a 256,000-character output limit, bounded protocol records, and explicit incomplete-stream detection. Empty or malformed output is not reported as success.

Only one active Run is allowed per conversation. Short SQLite transactions serialize send, regenerate, and settings changes. The worker releases transactions before every external wait and before closing the provider connection. Regeneration creates a child Run on the same Task, preserves earlier responses as superseded, and excludes them from later model context. Context includes at most the latest 16 eligible messages and 56,000 characters, plus an 8,000-character system prompt. Failed/partial assistant responses are excluded. The window starts with a user turn; consecutive messages of the same role are combined for compatibility with strict chat templates. No hidden summarization or automatic cloud fallback occurs.

Full history remains in SQLite. Conversation lists show the latest 100; message views show the latest 200. UI streaming uses the shared Run SSE endpoint with persistent-message refetching. Markdown never interprets raw HTML, and remote images are rendered as text so merely viewing a response does not fetch external resources.

[Rolling summaries](conversation-summaries.md) are explicit local-model Runs. Enabled summaries are snapshotted into future context; covered messages no longer consume the recent window. Text attachments, multiple configured providers, external AI, and tool execution remain later capabilities. Normal tests and `scripts/chat_smoke.py` use fake providers. Real local completion, including Docker access through the private runner bridge, is recorded in [verification](verification.md).

## Host loopback model access

Compose defaults to the [typed local-model bridge](local-model-bridge.md) over the existing private Runner socket. Model listing and bounded streamed completions target only the configured local endpoint, with no redirects or caller-selected URL. Canceling a Run closes the upstream response. Direct provider transport remains available for native development and explicitly configured container-reachable endpoints.
