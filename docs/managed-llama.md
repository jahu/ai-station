# Managed llama.cpp runtimes

llama.cpp and the configured OpenAI-compatible provider (including Ollama) coexist. Discovered GGUFs are loaded only by an explicit model selection, typically from a curated definition whose install Run has confirmed the file and the already-installed server image. The native Host Runner owns a narrow container adapter; the control plane receives neither a Docker socket nor model-root mounts.

A load Task creates a Run and a managed RuntimeInstance. Its immutable request binds the model path, observed size/mtime, selected discovered GPUs, context size and KV cache type. Coding Q8 loads treat the requested context as a GPU-fitting ceiling: the control plane persists the size it actually queued, and the Runner records observed `n_ctx` from read-only `/v1/models` and `/props` after `/health` succeeds. Missing runtime metadata does not block readiness and is not invented. The Runner uses an administrator-configured, already installed image, resolves its immutable image ID, mounts one model read-only and one private runtime directory, drops capabilities, runs as the workstation user and disables networking. llama-server listens on a Unix socket in that directory. No image/model download, driver change or external-runtime shutdown occurs.

Multiple GPUs use llama.cpp layer splitting with equal proportions across the explicitly selected devices. GPU reservations remain held while the runtime is loaded, independently of the completed load Run. Stop is a separate typed Run and releases reservations only after confirmed termination. The immutable native manifest and container ID/labels identify ownership across restarts. Repeating a load request for the same instance inspects/resumes its create/start journal; it never creates a second container or restarts an exited instance. Recovery can safely resume that operation. External containers are never adopted.

Inference uses the private Runner bridge and a runtime ID, not a caller URL. A stored conversation retains its model identity. After the first explicit load records GPU and context choices, Chat, summaries, the assistant and agents automatically reload a stopped model using those choices. Concurrent consumers share one pending load. Changing runtimes never silently substitutes another model.

When an image or another managed model needs reserved GPUs, the worker queues stop Runs for idle AI Station-owned llama.cpp instances. Queued or active consumers protect their model from eviction. External providers such as Ollama remain untouched. Stops and loads are ordinary inspectable Runs; failed prerequisites fail the dependent Run before execution. Canceling a waiting consumer does not cancel a shared load.

Durable RunDependency edges determine scheduling independently of parent_run_id provenance. Workers skip blocked Runs and continue unrelated work. SQLite transactions serialize load reuse and eviction against new consumers. A new request during a stop waits for that stop, a fresh load and then inference. GPU reservations are released only after the Runner confirms termination.

Configuration: `AI_STATION_LLAMA_IMAGE` selects an already-installed llama.cpp server image. Its CLI must support `--host /runtime/model.sock`, `--split-mode layer`, `--tensor-split`, `--gpu-layers` and `--parallel`, `--reasoning` and `--reasoning-budget`. Interactive runtimes request reasoning off with a zero thinking budget so thinking-only output cannot consume the entire final-response budget. These flags are documented by [llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) and were verified against the installed image help. Docker/NVIDIA Container Toolkit compatibility is checked by actual startup. No driver is installed or changed.

## Verified local acceptance (2026-09-27)

Real tests used the installed llama.cpp server image with CUDA 12.8, build b11011. The 27B RVN Q4_K_M GGUF loaded across two discovered RTX 3060 devices, answered through the private Runner bridge and unloaded through a stop Run, releasing both resource locks. A browser test selected that model, created a conversation and displayed its actual response. The 9B Q6_K GGUF independently passed load/chat/stop on one GPU. Model files and the external Ollama service were unchanged. These tests used isolated application databases.

The installed CUDA 13 server image required CUDA 13.3 and failed its driver compatibility check; the existing CUDA 12.8 image worked without any host changes. The 27B IQ2_XS variant is discoverable but has not yet been smoke-tested in this increment.

Automatic orchestration was also tested on the workstation in an isolated data root: load 9B on one GPU → an ordinary Juggernaut 256×256/4-step image Run queues owned model stop → real image artifact → a new Chat message queues 9B reload → final response “Dwa plus dwa wynosi cztery.” This passed with a 512-token response budget after explicitly disabling thinking for interactive runtimes. Earlier attempts at 512 and 2048 tokens produced no final text with automatic thinking; those attempts were failures, not successful chat acceptance. All smoke-owned containers were stopped afterward; the preview and external Ollama were unaffected.

The chat model catalog excludes files named as `mmproj` companions (case-insensitive tokens separated by dots, dashes or underscores). They remain in the general model registry and are not launched as standalone language models.

## Model selection UX

Chat presents one searchable model picker, grouped into on-disk llama.cpp GGUFs and the configured local server. GPU/context settings are optional advanced controls for a first load. Choosing **Use model** starts that first load as a normal Run; existing saved models reload on demand. The conversation header offers the same picker and preserves other conversation preferences when switching. Busy conversations cannot change models. Failed load requests keep the previous choice, and unknown runtime ownership requires inspection.

The Platform assistant can queue the same load and stop Runs as typed conversation actions after the user selects a discovered GGUF or an owned instance. A model-generated plan cannot grant `manage_models` or stop an external runtime.
